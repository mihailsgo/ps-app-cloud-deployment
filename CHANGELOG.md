# Changelog

## v1.0.21

- Fixed `signed-output/` and `docs/` being created with `chmod 777` ([psapp-saas#7](https://github.com/mihailsgo/psapp-saas/issues/7)), duplicated in three places (`bootstrap.sh`, `upgrade.sh`'s `mig_signed_output_apply`, and referenced in `validate-config.sh`'s remediation text). Checked what each mounting container actually needs before picking a mode, not a guess: `signed-output/` is mounted only into `ps-server`, confirmed live (`docker run --rm --entrypoint id mihailsgordijenko/ps-server:3.28` → `uid=0`) to always run as root because `psapp/server/Dockerfile` has no `USER` directive — root bypasses host permission checks on a normal Docker install, so 777 never actually helped the container write, it only widened host-side exposure of what can be real signed customer documents; now `chmod 750`. `docs/` is mounted only into `dmss-archive-services-fallback`, confirmed live (`docker run --rm --entrypoint id trustlynx/dmss-archive-services-fallback:24.0.5 spring` → `uid=999 gid=1000`) to run as a real non-root user; now `chmod 770`, group-owned to that gid, resolved dynamically at run time (reads the pinned tag, falls back to today's known gid with a loud warning if resolution fails) rather than hardcoded. Both now live in one shared `installation-scripts/lib/dir-permissions.sh` instead of three independent copies; kept v1.0.16's "chmod silently no-ops on a Docker-auto-created root-owned directory" insight as a post-check warning, adapted to the new modes/group (`sudo chgrp`/`chmod`, not `sudo chmod 777`). `validate-config.sh` now actively fails if either directory is world-writable, not just non-writable. There is no clean narrower fix for `signed-output/` without adding a non-root `USER` to the `ps-server` image in the separate `psapp` repo — flagged explicitly rather than papered over.
- Added `installation-scripts/diff-baseline-overlay.sh --baseline <git-ref-or-path>`, which diffs a live checkout's four per-host-mutated files (`nginx/nginx.conf`, `config/constants.json`, `config/config.js`, `docker-compose.yml`) against a clean baseline and classifies every difference as expected overlay (a known field `configure-host.sh`/`upgrade.sh` document rewriting) or unexpected drift. Verified on real Linux against synthetic scenarios: zero drift when baseline equals live, clean pass when only known-overlay fields differ (hostname, image tag, secret-bearing fields), and correctly flagged an injected stray hand-edit and a stray JSON key as drift with a non-zero exit.
- Originally added `installation-scripts/lib/deployment-evidence.sh` here; superseded before landing by the independently-written, schema-compatible superset added below in v1.0.19 (same `write_deployment_evidence()` interface, plus image digests and restart-count deltas this version didn't have) — that version is what ships. `bootstrap.sh`/`upgrade.sh` writing `deployment-evidence.json` (git-ignored) with this repo's git revision/dirty flag, image tags/revisions, and config checksums was this change's contribution to that shared design.
- `.gitignore`: added `*.bak` (the per-run backups `bootstrap.sh`/`configure-host.sh`/`upgrade.sh` create were previously untracked but not excluded) and `signed-output/**` (holds real signed documents, unlike `docs/**` which was already covered).
- Added [41. Baseline/Overlay Reconciliation](documentation/41-baseline-overlay-reconciliation.md), documenting all of the above and stating plainly what still needs a human with access to the actual production host — this release is repo-side tooling only, not a reconciliation of any specific deployed host. Also added the [40. Reliability and Rollback](documentation/40-reliability-and-rollback.md) section (and its four sub-pages) to `README.md`'s content map, which v1.0.19 below had introduced without a link.

## v1.0.20

- Pinned every image `docker-compose.yml` references to an immutable `sha256` digest, not just a tag ([psapp-saas#11](https://github.com/mihailsgo/psapp-saas/issues/11)): a tag can be moved or overwritten upstream, so the same compose file could previously deploy different content at different times with no way to detect it. Retagged `nginx:latest` to the explicit `nginx:1.30.5` (nginx's `stable` line — `latest`/`mainline` currently resolve to `1.31.6`) before digest-pinning it, since pinning `latest`'s digest as-is would have frozen an arbitrary, non-reproducible build. Every digest was resolved against the live registry and re-pulled by its exact `repo:tag@digest` string to confirm it's real, not guessed. No `certbot` service exists anywhere in this repository (confirmed independently; see [psapp-saas#10](https://github.com/mihailsgo/psapp-saas/issues/10)) — nothing to pin there.
- Added `release/approved-digests.json`, a new registry (matching the existing `release/capabilities.json` pattern) recording the digest approved for each pinned image. `installation-scripts/validate-config.sh` gained an "Image digest pinning" check that fails a deployment whose `docker-compose.yml` pin is missing a digest or doesn't match this registry — the literal "deployment validation rejects missing or unapproved digests" requirement. Shared reader helpers live in the new `installation-scripts/lib/digests.sh`.
- Added `installation-scripts/check-digest-drift.sh` — read-only, for manual or scheduled review, never auto-updating: compares `release/approved-digests.json` against what `docker-compose.yml` actually pins and what each registry currently serves for the same tag, printing one `DRIFT:` line per disagreement. Verified locally against the live registries (clean run), and against an intentionally corrupted digest (correctly reported as drift, then reverted).
- Fixed a bug `upgrade.sh`'s tag-bump introduced once digests were pinned: its `sed` only replaced the numeric tag, which would have silently left the *old* image's digest attached to the *new* tag — an actively wrong pin, not just an incomplete one. The tag-rewrite now also strips any existing `@sha256:...`, and prints a reminder that the new reference needs to be digest-pinned again before the deployment is complete.
- Closes the gap v1.0.19's `rollback.sh` stated plainly it had left open ("Digest-exact ... rollback is a stated follow-up, blocked on psapp-saas#11 ... not yet landed"): `rollback.sh` restored image tags with the same bare-tag `sed` as `upgrade.sh` did before this release, which would have carried a *stale* digest forward onto a *rolled-back* tag now that `docker-compose.yml` pins by digest. It now reads the digest each snapshot's `manifest.json` already recorded (`lib/rollback-snapshot.sh` was already capturing it via `docker inspect`, just not acting on it) and restores the exact `tag@digest` pin that was running before the upgrade it's undoing, falling back to a stale-digest-stripped bare tag with a re-pin reminder for snapshots that predate digest pinning. Verified in isolation (see PR).
- Added `psapp/.github/workflows/build-and-push.yml` (this repository had no CI at all before) — builds `ps-client`/`ps-server` on a `ps-client/*`/`ps-server/*` tag push (the same tag-anchoring scheme the manual release procedure already uses) with `docker buildx build --sbom=true --provenance=mode=max`, publishing an SBOM and build-provenance attestation alongside the image. **Triggered and verified for real** with a genuine `ps-server/3.29` tag push (CI-verification only — no functional change, not adopted as the deployed release): the tag-anchor check, Docker Hub login (after correcting the `DOCKERHUB_TOKEN` secret, which was initially rejected — `unauthorized: incorrect username or password` — until reset to a valid Docker Hub access token), build, and push all succeeded; `docker buildx imagetools inspect mihailsgordijenko/ps-server:3.29` confirms a real SPDX SBOM (generated by Syft v1.51.0) and a real SLSA provenance document (showing the exact build-args used, including `GIT_REVISION` matching the tagged commit) both attached to the pushed image.
- Scaffolded `renovate.json` for automated digest-update PRs (Renovate's `docker-compose` manager, `pinDigests: true`). Requires enabling the Renovate GitHub App (or a self-hosted runner) on the repository, which this change does not and cannot do; needs no additional secrets since every pinned image is public.
- Extended [39. Release Procedure](documentation/39-release-procedure.md) with a required digest-pinning step, a third-party-image (Nginx/Keycloak/DMSS) pinning note, and digest/SBOM/provenance verification commands; [1. Release Snapshot](documentation/01-release-snapshot.md) now points at `release/approved-digests.json` and lists the three images it previously omitted (Nginx, the local e-sealing stamping service, the deployment wizard); [40.4](documentation/40-04-rollback.md)'s "known limitation" section is updated to reflect the `rollback.sh` fix above; the rollback sections in [5.2](documentation/05-02-upgrade-to-the-current-release.md) and [4.4](documentation/04-04-existing-deployment-upgrade-an-already-deployed-instance.md) now point at `rollback.sh` as the preferred path and describe the manual fallback for pre-`rollback.sh` situations.

## v1.0.19

- Added `healthcheck:` to every long-running service in `docker-compose.yml` and rebuilt `depends_on:` around `condition: service_healthy` throughout ([psapp-saas#12](https://github.com/mihailsgo/psapp-saas/issues/12)). Previously there were zero health checks and two `depends_on` entries whose direction was backwards (`ps-server` depended on `nginx`; `nginx` depended only on `ps-client`) — a container could report `running` while Keycloak's realm, the archive service, or the container-signature service wasn't actually ready. Each probe was picked by exec-ing into the real running container and testing what's actually there (several images ship without `curl`/`wget`): Keycloak needed `KC_HEALTH_ENABLED=true` and, non-obviously, its health endpoint moves to a separate management port (9000) that's still prefixed by `KC_HTTP_RELATIVE_PATH`; `ps-server`'s `/health` is real but Keycloak-Bearer-protected by design, so the check accepts 200 or 401; one DMSS service's own auth filter returns a consistent 403 on `/actuator/health`, accepted for the same reason. `ps-server` now waits on Keycloak + the archive/container-signature services; `nginx` now waits on both `ps-client` and `ps-server`. Verified by bringing the stack down and up from scratch and confirming the dependency graph is actually respected (each service visibly waits for `Healthy` before starting) and all 8 services settle on `healthy`. Merged alongside v1.0.18's port-binding hardening below — the two touch the same `docker-compose.yml` blocks (this adds `healthcheck:`, that removed/loopback-bound `ports:`) and combine cleanly. Documented in [40.1](documentation/40-01-health-checks-and-startup-order.md).
- Added `installation-scripts/postdeploy-check.sh`, chaining `validate-config.sh` + `verify-keycloak.sh` + `verify-served-cert.sh` (none of which were previously wired together) with new checks for the HTTPS→`/portal/` redirect, served-vs-configured portal runtime config, the Keycloak discovery endpoint, and unauthenticated-request rejection on a protected API route. Has a clearly-labeled, non-failing `SKIPPED` slot for the authorized signing smoke test tracked as [psapp-saas#9](https://github.com/mihailsgo/psapp-saas/issues/9), which had not landed a real (non-mocked) authenticated test at the time this was written — verified `psapp/client/tests/e2e/sign-flow.spec.js` mocks every API call and is not a substitute. An authenticated-access check via `smoke-user.sh` was designed and then dropped: `print_secret()` (`lib/kcadm.sh`) deliberately never writes a generated password anywhere a script could capture, which is exactly the property that made it unusable here — documented in [40.2](documentation/40-02-post-deploy-validation.md) rather than worked around.
- Added `installation-scripts/monitor-status.sh`, a read-only observability report (container health/restart counts, certificate days-to-expiry, stamping/archive/routing failure counts grepped from real existing log markers, disk usage, and a best-effort signed-PDF buffer proxy) — explicitly not an alerting system. [40.3](documentation/40-03-monitoring-and-alerting-proposal.md) proposes how these feed a real alerting stack without picking one, and states plainly that standing one up was out of reach for this change. The one real, stated gap: `psapp/server/lib/signedPdfBuffer.js` exposes no live stats getter today, so continuous buffer-growth monitoring needs a small `psapp` change not made here.
- Added `installation-scripts/rollback.sh` plus a new pre-mutation snapshot step in `upgrade.sh` (`lib/rollback-snapshot.sh`): every `upgrade.sh` run now writes a timestamped, non-overwriting snapshot of `docker-compose.yml` and `config/config.js` (with an image-digest/tag manifest) *before* touching either file, replacing the old single-generation `.bak` pair that a second run would silently destroy. `rollback.sh --yes` restores the image tags (a targeted `sed`, not a wholesale overwrite, so later unrelated `docker-compose.yml` edits survive) and `config/config.js`, then waits for the restored services to report healthy — never touching `signed-output/`, `docs/`, `nginx/nginx.conf`, or `config/constants.json`. Tested for real, twice: a simulated failed `ps-client` upgrade (nonexistent tag) and a simulated failed `ps-server` upgrade, each followed by a rollback that restored the working tag, left a `signed-output/` marker file untouched, and reported all services healthy again; a second consecutive `rollback.sh --yes` run confirmed it's a no-op the second time. Digest-exact (rather than tag-based) rollback is a stated follow-up, blocked on [psapp-saas#11](https://github.com/mihailsgo/psapp-saas/issues/11) (image digest pinning), not yet landed. Documented in [40.4](documentation/40-04-rollback.md).
- Extended `lib/deployment-evidence.sh` (new; schema mirrors the one in the still-open [psapp-saas#7](https://github.com/mihailsgo/psapp-saas/issues/7) PR, reimplemented rather than merged in directly — see that file's header comment for why) to additionally record real running image digests (via `docker inspect`, independent of whether `docker-compose.yml` pins by digest yet) and per-service restart counts/deltas since the previous snapshot. Called from `bootstrap.sh`, `upgrade.sh`, and `postdeploy-check.sh`. Fixed two bugs found while testing this against a real stack: tag extraction used `grep -oP`, which isn't available under every `grep` (BusyBox/Alpine, and the MSYS grep this was first tested under) — switched to the `sed -nE` pattern `upgrade.sh`'s own `current_tag()` already uses for the identical reason; and per-service `docker inspect` was looking up containers by their *compose service name*, which silently returns nothing for `keycloak` on any real deployment (it has no `container_name:` override) — fixed to resolve the real container id via `docker compose ps -q` first.
- Fixed `installation-scripts/smoke-user.sh` shipping without the executable bit (git mode `100644`, inconsistent with every other top-level script and the v1.0.13 fix that was supposed to cover all of them) — found while setting the same bit on the three new scripts above.
- `.claude/skills/padsign-deploy/SKILL.md` and its `.agents/` mirror updated with the three new scripts and the new `rollback.sh`-based recovery procedure.

## v1.0.18

- Fixed internal services (Keycloak, `dmss-archive-services`, `dmss-container-and-signature-services`, `dmss-archive-services-fallback`, `ps-server`) publishing to all host interfaces by default ([psapp-saas#13](https://github.com/mihailsgo/psapp-saas/issues/13)): bare `host:container` compose port syntax binds `0.0.0.0`, meaning a permissive or misconfigured AWS security group was the *only* thing standing between the internet and every one of these services, bypassing nginx's TLS, routing, and auth entirely. Found along the way: `nginx/nginx.conf`'s `/archive/api/` and `/container/api/` routes reached the archive and container-signature services via `http://host.docker.internal:86|84/api/` — a hairpin out of the container and back through the host-published port — while `/api/` and `/auth/` already used internal Docker service names; fixed first (`dmss-archive-services:8090`, `dmss-container-and-signature-services:8092`), and verified live (all routes, before and after, real curl output) before touching any port, since removing the ports first would have broken document downloads and e-sealing. Keycloak (8080) and the archive/container-signature services (86, 84) are now bound to `127.0.0.1` only — genuine host-level dependencies exist for all three (the Windows `keycloak-bootstrap.ps1` dev script, and the direct-`curl` operator diagnostics in [4.4](documentation/04-04-existing-deployment-upgrade-an-already-deployed-instance.md) and [4.7](documentation/04-07-adding-a-new-signing-profile-end-to-end.md)) so loopback binding was chosen over full removal, and those docs now note the loopback-only caveat (host or SSH tunnel). `ps-server` (3001) and `dmss-archive-services-fallback` (93) have no host port at all — nothing in this repo (config, scripts, or docs) ever reached either through the host. The Deployment Wizard (8443) is unchanged: already profile-gated and already documented ([36.5](documentation/36-05-security-considerations.md)) as a deliberate exception with its own HTTPS+token controls. `installation-scripts/validate-config.sh` gained a "Port bindings" check (via `docker compose config --format json`, already a script dependency) that fails on any service — the five named here, or any future one — publishing to a non-loopback interface without an explicit allow-list entry (`nginx`, `wizard`); verified it flags all five original bindings against the pre-fix compose file and passes cleanly against the fixed one.

## v1.0.17

- Fixed `keycloak-bootstrap.sh` printing its generated demo `test`-user password in plaintext to stdout ([psapp-saas#6](https://github.com/mihailsgo/psapp-saas/issues/6)): `bootstrap.sh`'s "filter secrets" step only ever stripped the `BACKEND_CLIENT_SECRET=` line, so the test password reached `bootstrap.sh`'s own captured output and, when run through the deployment wizard, its retained live-log buffer. - Added `installation-scripts/smoke-user.sh create|delete` — a least-privilege way to provision and remove a short-lived, uniquely-named Keycloak login assigned exactly one existing company role (never `padsign-admin`), without touching the shared `test` account, its realm/client/role setup, or restarting Keycloak. `delete` refuses a username that doesn't look like one of its own unless `--force` is passed, and treats deleting an already-gone user as success. Documented in a new [14.2](documentation/14-02-automated-setup-recommended.md) section; verified locally by running the create/delete cycle twice consecutively against a live Keycloak 26.3.2 container and confirming the user was actually gone each time.
- Extracted `installation-scripts/lib/kcadm.sh` (following the existing `lib/capabilities.sh` pattern) for the `kc_exec`/readiness-wait/login/CSV-parsing helpers that `keycloak-bootstrap.sh` and `verify-keycloak.sh` previously duplicated verbatim; both scripts now source it instead, with no behavior change (verified live).
- Fixed `verify-keycloak.sh`'s three JSON-validation checks (frontend client, backend client, test-user role mapping), which never actually ran: each combined a `python3 - <<'PY' ... PY <<<"$json"` heredoc with a trailing herestring on the terminator line, which is invalid — bash never recognized `PY <<<"$json"` as ending the heredoc, so it silently swallowed the rest of the script as literal heredoc body, python3 raised a `SyntaxError` on that stray line, and every check after the first client existed-check simply never ran. Found while verifying this release's `verify-keycloak.sh` refactor locally — `bash -n` failed outright on the unmodified script. Fixed by supplying the Python program via `python3 -c "$(cat <<'PY' ... PY)"` instead, freeing stdin for the JSON payload; the Python bodies themselves are unchanged.
- Added [14.7 Break-glass: recovering when no Keycloak credential works at all](documentation/14-07-break-glass-admin-recovery.md), distinct from [37.5](documentation/37-05-known-gaps-keycloak-admin-password-rotation.md) (which requires some currently-working credential to start from): documents Keycloak's own `kc.sh bootstrap-admin user` recovery command, verified locally against this repo's pinned image, including the restart it requires and the realm/user data it preserves.

- Added [37. Settings (Post-Go-Live Changes)](documentation/37-settings-post-go-live-changes.md) — a new wizard section (`/settings`, topbar link next to Dashboard) letting an operator change hostname, renew the TLS certificate, or toggle document routing/demo mode/local e-sealing on an *already-deployed* stack, none of which was previously possible without hand-chaining scripts. Three new orchestrator scripts wrap the existing engines: `update-hostname.sh` (chains `configure-host.sh` + `keycloak-bootstrap.sh` + restarts nginx/ps-server), `renew-cert.sh` (cert swap + nginx restart), `toggle-features.sh` (any combination of the 3 flags in one pass, restarting only what's needed). `configure-host.sh` gained symmetric `--disable-routing`/`--disable-demo`/`--disable-local-eseal` flags; `keycloak-bootstrap.sh` gained `--skip-test-user` so a live hostname change never resets the demo `test` account.
- Fixed `configure-host.sh --company-role` silently never updating `config.js`'s `DEMO_COMPANY_ROLE`: the replacement regex anchored `$` immediately after the closing quote, but the real field has a trailing comma, so the anchor never matched and the field stayed at its `"CHANGE_ME"` template default regardless of what was passed. Found live while building the Settings hostname-change feature, which reads this field back to avoid re-asking the operator for it.
- Fixed `keycloak-bootstrap.sh`'s `ensure_role()` throwing `Illegal character in path` for any multi-word role name (e.g. `"Acme Corp"`) once it already existed: the existence check did `kcadm get roles/<name>`, a raw URL path segment that Keycloak's admin CLI rejects outright when it contains a space, so it always fell through to `create`, which then failed on a duplicate-name conflict. Replaced with a full-list-plus-exact-match check (`get roles --fields name` filtered client-side), the same technique already used for clients/users elsewhere in the file. This was dormant until the `DEMO_COMPANY_ROLE` fix above made the role name reach this code path correctly for the first time.
- Fixed a `set -euo pipefail` robustness gap across `update-hostname.sh`/`renew-cert.sh`/`toggle-features.sh`: several post-action verification checks (a live TLS handshake, a config-file readback) were best-effort/informational by design, but a transient failure or simple no-match in their pipeline (a real `grep`/`openssl` exit code, not a script bug) silently aborted the *entire* script under `pipefail` before reaching the intended graceful-WARNING fallback — meaning an otherwise fully successful certificate renewal or feature toggle could report as a hard failure. Every such check now ends in `|| true`. Found via a live E2E run where a successful cert renewal reported `success:false`.
- Fixed a live-state bug in the wizard's Settings page: `readConfiguredFeatures()`'s `localEsealProvisioned` field (meant to distinguish "never enabled" from "enabled once, now off") checked `docker-compose.yml` for the `dmss-digital-stamping-service` block — but that block, and the demo `seal.p12`/`application.yml` under `dmss-digital-stamping-service/`, ship pre-committed in every checkout rather than being inserted on first `--enable-local-eseal` as assumed, so the field was always `true` and the Feature Toggles card's "(not yet provisioned)" hint could never render. Removed the dead field and its hint; `localEseal` itself (`STAMP_MODE`'s presence in `config.js`) was already the correct live signal.
- Added `installation-scripts/verify-served-cert.sh` and [11.2 Monitoring the Served Certificate](documentation/11-02-monitoring-the-served-certificate.md) — an over-the-wire check that opens a real TLS handshake and compares the certificate nginx is **serving** against the one on disk. This closes a detection gap that no existing check could see: nginx reads its `ssl_certificate` files only at startup and on reload, so an ACME renewal that copies a new fullchain into `nginx/certs/` but whose reload step fails leaves nginx serving a months-old certificate until it expires — while renewal logs report zero failures, the file on disk is current, and `validate-certs.sh` passes every one of its checks. Found live on a deployment whose renewal hook ran `docker kill -s HUP nginx || true` inside the ACME client container, which ships no `docker` binary: the reload failed on all 335 iterations with `sh: docker: not found`, `|| true` erased the error, and unrelated upgrade restarts accidentally masked it until deployments paused for longer than the certificate's remaining life. The script is detection-only — it never reloads or mutates anything — and `validate-certs.sh`'s header now states that it is file-level only and points here. The wizard's Settings TLS card gained a second, read-only "What nginx is actually serving" checklist backed by `certValidator.js`'s new `checkServedCert()` (published as `padsign-wizard:0.1.1`); it passes `--connect nginx:443` explicitly, because the wizard runs these scripts inside its own container where `localhost:443` is nothing, and unlike `runValidateCerts()` it never rethrows on a non-1 exit — `GET /settings` does `next(err)`, so a missing script or a timed-out handshake must degrade one card rather than blank the whole page.
- Fixed all `installation-scripts/*.sh` shipping without the executable bit (git mode `100644`): on a fresh Linux clone every documented `./installation-scripts/bootstrap.sh ...` invocation failed with `Permission denied` until the operator ran `chmod +x ./installation-scripts/*.sh` — and since `bootstrap.sh` invokes its child scripts directly (`configure-host.sh`, `validate-certs.sh`, `keycloak-bootstrap.sh`), the bit was needed on every script, not just the entry point. The scripts are now committed with mode `100755` (`keycloak-bootstrap.ps1` is unaffected), the `chmod +x` workaround step is gone from [3. Quick Start](documentation/03-quick-start-new-deployment.md), [14.2 Automated Setup](documentation/14-02-automated-setup-recommended.md), and [24.1 Deployment Checklist](documentation/24-01-deployment-checklist-recommended.md), and the scheduling note in [11.2 Monitoring the Served Certificate](documentation/11-02-monitoring-the-served-certificate.md) no longer claims the scripts ship non-executable.
