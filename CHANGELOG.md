# Changelog

## v1.0.40

- **Fixed: Keycloak passwords were still in the host process list during `keycloak-bootstrap.sh`, `verify-keycloak.sh` and `smoke-user.sh`**, and so during `bootstrap.sh`, `update-hostname.sh`, `postdeploy-check.sh` and `signing-smoke.sh`, which call them. v1.0.26's `kc_exec_with_secret` kept the password off the host-side `docker compose exec` command line, but the container's shell expanded `--password "$KC_SECRET"` / `--new-password "$KC_SECRET"` into the command line of `kcadm.sh` and its java process. Container processes are ordinary host processes, so every local user saw it with `ps -ww`. Now:
  - `kc_login` goes through `kc_exec_with_cli_password` (v1.0.36): no `--password`, the password reaches kcadm as the container's `KC_CLI_PASSWORD`.
  - `kcadm.sh set-password` only takes the new password on its command line, so it is no longer used. The new `kc_set_password` (`lib/kcadm.sh`) sends the credential JSON to `users/<id>/reset-password` on stdin. The JSON is written by bash's `printf` builtin, which starts no process, so the password is in no command line and no environment. It escapes `\` and `"`. This covers the `test` user and `--users` in `keycloak-bootstrap.sh`, and the smoke user in `smoke-user.sh`.
  - `kc_exec_with_secret` is removed; nothing uses it any more.
- **Fixed: scripts, and the deployment wizard, handed the Keycloak admin password to each other on the command line.** `bootstrap.sh` passed `--admin-pass` to `configure-host.sh` and (next to `KEYCLOAK_ADMIN_PASSWORD`, which it already set) to `keycloak-bootstrap.sh`. `update-hostname.sh` passed it to `keycloak-bootstrap.sh`, `postdeploy-check.sh` to `verify-keycloak.sh`, and the wizard to `bootstrap.sh` / `update-hostname.sh`, where it stayed in the process list for the whole run. All of them now use the environment: `KEYCLOAK_ADMIN_PASSWORD`, which `keycloak-bootstrap.sh`, `verify-keycloak.sh`, `smoke-user.sh`, `bootstrap.sh` and now also `update-hostname.sh` read when `--admin-pass` is absent. `configure-host.sh` reads `CONFIGURE_HOST_ADMIN_PASS` and `CONFIGURE_HOST_BACKEND_SECRET` (a flag still wins), and `bootstrap.sh` passes the backend client secret that way instead of `--backend-secret`. `configure-host.sh` also no longer interpolates the backend secret into the source of a `perl -e` command, which put it on perl's command line and broke on a secret containing `/` or `$`. `scriptRunner.startRun` takes an `env` that is kept on the run state, so **Retry** still works. The wizard's review step shows the command as `KEYCLOAK_ADMIN_PASSWORD=**** bootstrap.sh ...`.
- Docs: [42](documentation/42-host-reconciliation-runbook.md) secret-handling rule 1 is corrected. It said v1.0.26 left the password in 0 of 1578 process-list snapshots. Re-measured, v1.0.37 still leaked it, and the old figure is most likely an artifact of a `ps` that cuts lines at the terminal width (numbers below). [14.7](documentation/14-07-break-glass-admin-recovery.md), [37.5](documentation/37-05-known-gaps-keycloak-admin-password-rotation.md) and [42.2](documentation/42-02-keycloak-admin-access-and-smoke-identity.md) K1a, K2, K3 and K5 use `KC_CLI_PASSWORD` for kcadm logins and stdin JSON to `reset-password` instead of `set-password --new-password`; [42.5](documentation/42-05-rollback.md) follows. [40.5](documentation/40-05-production-safe-signing-smoke-test.md) no longer names `kc_exec_with_secret`. [36.5](documentation/36-05-security-considerations.md) no longer says the wizard exposes the admin password in the process list. [37.2](documentation/37-02-changing-hostname-after-go-live.md) passes it to `update-hostname.sh` through `KEYCLOAK_ADMIN_PASSWORD`. `AGENTS.md` and the `padsign-deploy` skill (both mirrors) are updated.

## v1.0.39

- Removed `installation-scripts/keycloak-bootstrap.ps1`, the Windows-only Keycloak bootstrap. It no longer worked and could not be made safe without a full second copy of `keycloak-bootstrap.sh`:
  - It did not parse on Windows PowerShell 5.1. `$ErrorActionPreference` came before `param(...)`, and the redirect-URI line used `\"`, which is not a PowerShell escape ("Unexpected token").
  - Its readiness check polled `http://localhost:8080/auth/health/ready`. With `KC_HEALTH_ENABLED`, Keycloak 26 serves health on the management port 9000, so the check could only time out.
  - It put secrets on command lines. The kcadm login expanded `--password "${KEYCLOAK_ADMIN_PASSWORD:-admin}"` into kcadm's argv inside the container, which the host's `ps` lists. The `test` user's password was inlined into the `docker compose exec` argv, and it was just the lowercased company role.
  - It never created the `padsign-backend-audience` mapper ([14.8](documentation/14-08-token-audience-for-introspection.md)), so on the pinned Keycloak a realm it built would log in but return 401 on every API call. It also left out the `test` user's first and last name and the client `name` fields.
- On a Windows development machine, run `keycloak-bootstrap.sh` (and every other script) from Git Bash or WSL. It reaches Keycloak through `docker compose exec`, not the host port. Linux stays the only supported deployment target.
- Keycloak's `127.0.0.1:8080` host port is unchanged. It is still used for local `curl localhost:8080` diagnostics, and the `docker-compose.yml` comment now gives only that reason.
- Docs: [9](documentation/09-prerequisites.md), [14.2](documentation/14-02-automated-setup-recommended.md), `AGENTS.md`, and the `padsign-deploy` skill (both mirrors).

The duplicate `source` of `lib/deployment-evidence.sh` in `bootstrap.sh` is removed as well.

It removes the user entry and the archive document (`DELETE /api/document/{id}`, sent from inside ps-server so it also works where nginx restricts `/archive/api`), the Keycloak client and the smoke user/role, the kcadm session file and the temporary directory. ## v1.0.35

Two supply-chain gaps from [psapp-saas#11](https://github.com/mihailsgo/psapp-saas/issues/11).

- **The image digest gate now covers the effective compose model.** `compose_image_refs` / `digest_from_compose` (`lib/digests.sh`) only grepped `docker-compose.yml`, so an image in a `COMPOSE_FILE` overlay (the section 42 `compose.overlay.yml`) got at most an "unpinned" warning from `overlay.sh verify` and was never checked against `release/approved-digests.json`. The model now comes from the new `installation-scripts/lib/digest_gate.py`: `docker compose config` from the project directory with every declared profile enabled (enumerated with `config --profiles`, since older compose releases do not accept `--profile '*'`), so `COMPOSE_FILE` / `.env` apply exactly as for `docker compose up` and the profile-gated stamping and wizard services stay covered. Without docker, or when compose cannot render the model, it reads the same files itself (`COMPOSE_FILE` from the shell environment, then `.env`, with `COMPOSE_PATH_SEPARATOR`; `docker-compose.override.yml` when `COMPOSE_FILE` is unset). A later file's `image:` replaces an earlier one's, which is compose's own merge rule. The gate's first output line says which way the model was read.
- The rules live in one place, `digest_gate.py check`, used by `validate-config.sh` (and so `postdeploy-check.sh`) and `check-digest-drift.sh`. Every service image must be digest-pinned and approved with its exact tag and digest, and every approved release image must be in the model. A tag-only overlay image, a digest-pinned image nobody approved, and an overlay replacing a release image (including the profile-gated wizard) with another digest all FAIL. `dmss-seal-smoke.sh` now boots the DMSS images of that same model.
- **Overlay-side approvals.** A host run as release baseline + overlay legitimately runs images the release does not ship (a DMSS version overlay, a host-only renewer, an older Keycloak if gate G1 keeps it). Those are approved in the overlay's own `approved-digests.json` (same schema, found via `.overlay-applied.json`'s `overlay_dir`). Each entry needs a `why`, and `ps-server`/`ps-client` can never be approved there (gate G2): both are FAILs. `check-digest-drift.sh` checks these entries against the registry too. `overlay.sh capture` carries the file over when it re-captures an overlay-managed checkout, and `rebase` already copies the whole overlay. Documented in [42.3](documentation/42-03-capturing-the-environment-overlay.md) O4 and [42.7](documentation/42-07-evidence-and-sign-off.md).
- **`upgrade.sh` refuses unapproved tags** (decision of 2026-09-24 on #11). A `--server-tag`/`--client-tag` that `release/approved-digests.json` does not approve now stops the run with exit 2, before the snapshot, any edit or any pull, like the capability gate. `--plan-only` refuses the same way, and so the deployment wizard's preview shows the refusal and never offers Apply. `--allow-unapproved` lets an emergency hotfix through: a warning banner, `UNAPPROVED OVERRIDE` in the text plan, `unapproved_override=<image>:<tag>:<approved tag>` in the machine plan, the tag left without a digest pin (so `validate-config.sh` keeps failing until it is approved), and a record in `deployment-evidence.json` under `"unapproved_override"`. That record is written by a failed upgrade too, and carried into later evidence (e.g. `postdeploy-check.sh`) while that tag is still pinned and still unapproved.
- **Combined with v1.0.34's signature pre-flight.** `upgrade.sh` now runs, in order: the capability gate and the approved-tag gate (both before the plan, so `--plan-only` refuses too), the plan-only exit, then the cosign signature pre-flight, and only then Step 1's snapshot and backups. v1.0.34 verified signatures after Step 1 had written the rollback snapshot. A signature that does not verify now leaves nothing written at all. `--plan-only` still does not call cosign, as in v1.0.34. With the approved-tag gate in front, the pre-flight's "digest the tag resolves to now" path is only reached through `--allow-unapproved`.
- New `installation-scripts/tests/test-digest-gate.sh` (27 cases, on a throwaway copy, never pulls or starts anything): the model cases via docker compose and via the file fallback, the upgrade refusal (plan and real run, nothing written), the override in both plan formats, the gate order against stub `cosign`/`docker` binaries (an unapproved tag never reaches cosign, `--plan-only` never calls it, a failing or unusable-but-required signature check leaves no snapshot, backup, edit or pull, and a verified one reaches Step 1), and the evidence record, carry-forward and drop. Passes under Git Bash and on WSL Ubuntu (bash 5.2, python 3.12, compose v5.3.1).
- Verified on WSL Ubuntu on a copy of this branch: `validate-config.sh --host` on the clean checkout prints `All checks passed.` with every image OK (no daemon reachable, so the running-container checks skip). With `COMPOSE_FILE=docker-compose.yml:/tmp/compose.overlay.yml` adding `redis:7@sha256:...` it fails with `FAIL service cert-renewer: ... has no entry in release/approved-digests.json - unapproved image`, also with docker absent from `PATH`. `upgrade.sh --server-tag 3.99 --allow-unapproved` against a stub docker whose pull fails printed the banner, recorded `unapproved_override` in the failed-run evidence, and pulled nothing else.
- Found, not fixed: `check-digest-drift.sh` reports that the registry now serves `sha256:b972f831...` for `nginx:1.30.5`, not the approved `sha256:0aa2d81d...`. `main` reports the same, so this is an upstream re-publish to review and re-pin, not caused by this change.

## v1.0.34

- **cosign signature verification for ps-server / ps-client** ([psapp-saas#11](https://github.com/mihailsgo/psapp-saas/issues/11), criterion 3). psapp's CI now signs every released image with a cosign key pair and attaches its SPDX SBOM and SLSA v1 provenance as signed attestations, with no keyless signing and nothing uploaded to the public Rekor log. This repo gets the public key, `release/cosign.pub`, and a new `installation-scripts/lib/signatures.sh` that runs `cosign verify` plus `cosign verify-attestation --type spdxjson` / `--type slsaprovenance1` with `--insecure-ignore-tlog=true` against a pinned digest.
- `validate-config.sh` gained an *Image signatures (cosign)* section for the pinned ps-server / ps-client digests. `upgrade.sh` verifies the requested images **before** it rewrites `docker-compose.yml` or pulls, by the approved digest (or the digest the tag resolves to now, for a tag this checkout does not approve), and refuses the upgrade with nothing changed if a signature does not verify.
- No cosign (or cosign older than v3, which cannot read v3 bundles) is a warning on a host, so existing deployments keep validating, and a failure under `CI=true` or `PADSIGN_REQUIRE_SIGNATURES=1`. A signature that does not verify, a missing key file, or an unreachable registry always fails.
- The two releases deployed before signing existed, `ps-server:3.28` and `ps-client:8.39`, are exempt by exact repository + digest in the closed list `release/unsigned-legacy-images.json` (warning, not failure), so a deployment on them, or rolled back to them, still validates. Nothing matches by tag or version range. `rollback.sh` does not verify signatures.

## v1.0.23

- Fixed a regression introduced by the Keycloak `26.3.2` → `26.7.4` bump ([Renovate digest PR #12](https://github.com/mihailsgo/ps-app-cloud-deployment/pull/12)). After it, the portal login worked but **every authenticated ps-server API call returned 401**. ps-server validates each call by introspecting the user's `padsign-client` access token *as* the confidential `padsign-backend` client (keycloak-connect's `grantManager.validateAccessToken`). Keycloak 26.4.12, 26.6.2, 26.7.0 and later refuse that introspection unless the introspecting client is in the token's `aud`, as the fix for [CVE-2026-37979](https://github.com/keycloak/keycloak/issues/49113). A stock `padsign-client` token carries only `aud: "account"`, so Keycloak answered `{"active": false}` and logged `INTROSPECT_TOKEN_ERROR ... reason="Client 'padsign-backend' is not in the token audience"`.
  - **Reproduced** in an isolated, Keycloak-only compose project (unique project name, no `container_name`, no host ports), using the real `keycloak-bootstrap.sh` and a scripted authorization-code + PKCE login through Keycloak's HTML login form. The same flow gave `active=true` on 26.3.2 and `active=false` on 26.7.4, and the real pinned `ps-server:3.28` image answered `GET /health` with a valid portal token with **HTTP 401**.
  - **Chose to fix forward instead of reverting the pin to 26.3.2.** 26.3.2 predates CVE-2026-37979 and the 15 other CVEs fixed in 26.6.2, and every future Keycloak bump would hit the same audience check.
  - **Fix:** an `oidc-audience-mapper` (`padsign-backend-audience`) on `padsign-client` puts `padsign-backend` into the access-token audience. `keycloak-bootstrap.sh` now creates it for new realms. Existing realms get it from a new `upgrade.sh` config-migration table entry, `keycloak-backend-audience`, which runs on every upgrade and is reported by `--plan-only`. It is the first table entry whose target is live Keycloak state rather than a file, so its predicate is a read-only probe: `kcadm --no-config` with inline credentials, so it writes no kcadm config, and a stopped container is reported, never started. The result is cached per run so the plan and the apply see the same answer.
  - **Admin credentials** for the probe come from `KEYCLOAK_ADMIN` / `KEYCLOAK_ADMIN_PASSWORD` if set, otherwise from the keycloak container's own environment. If Keycloak cannot be reached, the plan says why and the run prints a `WARNING` with the fix, then continues the upgrade.
  - **Additive:** any existing mapper that already grants the audience, including a hand-made one, counts as applied. Shared helpers live in `installation-scripts/lib/kcadm.sh`, and `verify-keycloak.sh` gained a matching check.
- **Verified for real on 26.7.4.** After the migration, the same login gives `aud: ["padsign-backend","account"]`, introspection returns `active=true`, and ps-server `GET /health` returns **HTTP 200** (still 401 with no token).
  - A session that logged in *before* the migration recovered on its next refresh-token grant, so no logout is needed.
  - Re-running bootstrap or upgrade never created a duplicate mapper; the plan correctly reports `already applied`.
  - A wrong admin password produced the documented warning, and the upgrade still exited 0.
  - The mapper is harmless on 26.3.2 (still `active=true`), and the documented manual `kcadm` recipe works as written.
- `renovate.json`: holds `quay.io/keycloak/keycloak` to the verified `26.7.x` line (same pattern as the nginx rule). Before a new minor is allowed, a human should re-run a real login plus introspection against it.
- **Docs:** added [14.8 Token audience for introspection](documentation/14-08-token-audience-for-introspection.md), covering the cause, symptoms, automatic handling, and manual admin-console and CLI steps. Added the mapper step to [14.5](documentation/14-05-create-client-for-frontend-manual.md), and the new step 7 to [5.1](documentation/05-01-what-upgrade-does-step-by-step.md). Updated `AGENTS.md` and the `padsign-deploy` skill (both mirrors).

## v1.0.18

- Fixed internal services (Keycloak, `dmss-archive-services`, `dmss-container-and-signature-services`, `dmss-archive-services-fallback`, `ps-server`) publishing to all host interfaces by default ([psapp-saas#13](https://github.com/mihailsgo/psapp-saas/issues/13)): bare `host:container` compose port syntax binds `0.0.0.0`, meaning a permissive or misconfigured AWS security group was the *only* thing standing between the internet and every one of these services, bypassing nginx's TLS, routing, and auth entirely.
