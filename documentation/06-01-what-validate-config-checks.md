# 6.1 What validate-config checks

1. **File existence** - verifies `config/config.js`, `config/constants.json`, `nginx/nginx.conf`, `docker-compose.yml` exist
2. **Syntax** - validates `constants.json` is valid JSON, `docker-compose.yml` passes `docker compose config`
3. **Feature checks** - `DOCUMENT_ROUTING` in config.js, `signed-output` volume mount in compose, `signed-output/` and `docs/` directories exist and every path in them is owned by the uid their container image runs as (skipped when Docker is unavailable), nginx root→`/portal/` redirect
4. **Permission checks** - fails if `signed-output/` or `docs/` is world-writable (mode 777 or anything else granting "other" write); see [installation-scripts/lib/dir-permissions.sh](../installation-scripts/lib/dir-permissions.sh) for the least-privilege ownership and modes each one should have instead
5. **Hostname consistency** (if `--host` provided) - verifies `server_name` in nginx, `KEYCLOAK_URL` in constants.json, `auth-server-url` in config.js, and the keycloak service's `KC_HOSTNAME` in docker-compose.yml all match. A mismatched `KC_HOSTNAME` is a FAIL, not cosmetic: Keycloak uses it as its fixed frontend hostname, so it renders that other host into the login form and redirects (browsers are sent there at login) and names it as every token's issuer. A `WARN` (not a failure) is printed if `KC_HOSTNAME` is unset, or if the nginx service's network aliases don't include the host (containers then reach `https://<host>/` via public DNS instead of directly). Fix either with `configure-host.sh --host <host>`, or on an existing deployment with `upgrade.sh`'s `compose-hostname` migration ([5.1](05-01-what-upgrade-does-step-by-step.md))
6. **Image tags** - shows current ps-server and ps-client versions from docker-compose.yml, checks they match the release snapshot in [1. Release Snapshot](01-release-snapshot.md)
7. **Image digest pinning** - checks the *effective* compose model: `docker-compose.yml` plus every file `COMPOSE_FILE` names (shell environment, then `.env`, as `docker compose up` reads them), with every profile enabled so the profile-gated stamping and wizard services are included. Fails unless every image of that model is pinned `tag@sha256:digest` with exactly an approved tag and digest, and unless every image in `release/approved-digests.json` is in the model. A tag-only pin, a changed digest, a relabelled tag, and an image nobody approved all fail, including one an environment overlay adds or replaces. On a host run as release baseline + overlay ([42](42-host-reconciliation-runbook.md)), an image may instead be approved by the overlay's own `approved-digests.json` ([42.3](42-03-capturing-the-environment-overlay.md)); the OK line then names that file and the entry's `why`. The first line of the section says how the model was read: `docker compose config`, or the files directly where docker is not installed. Offline; the registry side is `installation-scripts/check-digest-drift.sh`, which applies the same rules
8. **Image signatures (cosign)** - for `ps-server` and `ps-client`, verifies the pinned digest's cosign signature and its signed SBOM (`spdxjson`) and provenance (`slsaprovenance1`) attestations against `release/cosign.pub`. Needs cosign v3+ and registry access. A signature that does not verify is a FAIL; no cosign on the host is a WARN (a FAIL under `CI=true` or `PADSIGN_REQUIRE_SIGNATURES=1`); the two releases from before signing existed (`ps-server:3.28`, `ps-client:8.39`) are a WARN, exempt by exact digest in `release/unsigned-legacy-images.json`. See [40.2](40-02-post-deploy-validation.md#image-signatures-cosign)
9. **Running containers** (if Docker is available) - verifies running images match docker-compose.yml tags
