# 40.3 Monitoring and Alerting

`installation-scripts/monitor-status.sh` has two modes:

- **Report mode** (default) is a read-only snapshot. It prints the numbers below and always exits `0`. Useful for a handoff or a support ticket.
- **Alert mode** (`--alert`) evaluates the same numbers against thresholds, exits `1` when anything fired, and POSTs one JSON message per run to `ALERT_WEBHOOK_URL`. This is what runs from cron.
- **Webhook test** (`--test-webhook`) sends one harmless test message to the same webhook and prints the HTTP status. It checks nothing else and needs no running stack.

```bash
./installation-scripts/monitor-status.sh --host padsign.client.com            # report
./installation-scripts/monitor-status.sh --alert                               # alert
./installation-scripts/monitor-status.sh --test-webhook                        # one test message
```

## Setting up alerting

1. Add the receiver URL to `.env` next to `docker-compose.yml` (it is gitignored, and webhook URLs are secrets). On an overlay-managed checkout (runbook 42) `.env` is regenerated by `overlay.sh apply`: see [Where the URL goes on an overlay-managed host](#where-the-url-goes-on-an-overlay-managed-host).

   ```bash
   ALERT_WEBHOOK_URL=https://hooks.slack.com/services/T000/B000/XXXX
   # optional: the message shape, json (default) or teams (Microsoft Teams Workflows, see below)
   # ALERT_WEBHOOK_FORMAT=teams
   # optional, for receivers that want auth:
   # ALERT_WEBHOOK_AUTH_HEADER=Authorization: Bearer <token>
   ```

   An environment variable of the same name wins over `.env`. Docker Compose ignores all three; only the script reads them. The script prints only the scheme and host of the URL, and hands the URL and the auth header to `curl` on its standard input, so neither shows up in `ps` either.

2. Run it from cron as the user that runs `docker compose`:

   ```cron
   */10 * * * * cd /opt/padsign && ./installation-scripts/monitor-status.sh --alert >> /var/log/padsign-monitor.log 2>&1
   ```

3. Check it once by hand. `./installation-scripts/monitor-status.sh --test-webhook` must print `Result:    HTTP 2xx - delivered to ...`, and the message must show up in the receiver. Then `./installation-scripts/monitor-status.sh --alert`: with no problems it prints `No alerts.` and exits `0`. To see a real alert delivered end to end, run it with a threshold you are sure to cross, e.g. `ALERT_DISK_PCT=1 ./installation-scripts/monitor-status.sh --alert`.

Without `ALERT_WEBHOOK_URL`, alert mode still prints the alerts and exits `1`, so cron's own `MAILTO` or any wrapper that acts on a non-zero exit still works.

### Microsoft Teams (Workflows)

The Office 365 connector *Incoming Webhook* that Teams channels used to offer is retired. A Teams webhook is now made with the **Workflows** app, and its standard template only accepts a message that carries an Adaptive Card in `attachments`. Sent the plain `json` payload, the workflow URL still answers `202 Accepted`, then the flow fails and nothing appears in the channel. Set `ALERT_WEBHOOK_FORMAT=teams` for such a URL (see [Payload](#payload)).

Create the webhook (new Teams):

1. In the channel that should get the alerts, open **...** (More options) next to the channel name and choose **Workflows**.
2. Pick the template **Send webhook alerts to a channel** ("Post to a channel when a webhook request is received"). Search for "webhook" if it is not in the list.
3. Give the workflow a name, for example `PadSign alerts padsign.client.com`, and click **Next**. If Teams asks to confirm the connection to Microsoft Teams, confirm it.
4. Check the **Team** and **Channel** (they default to the channel you started from) and click **Add workflow**.
5. Copy the URL the last screen shows, then click **Done**. Anyone who has the URL can post into the channel: keep it out of tickets, chats and the repository.

The cards are posted as the person who created the workflow ("... via Workflows"), through that person's connection. Create it with an account that stays, or re-create it when its owner leaves.

Put the URL and the format where the script reads them:

```bash
ALERT_WEBHOOK_URL='https://prod-00.westeurope.logic.azure.com:443/workflows/.../triggers/manual/paths/invoke?api-version=2016-06-01&sp=...&sv=1.0&sig=...'
ALERT_WEBHOOK_FORMAT=teams
```

Keep the single quotes: the URL contains `&`, which a shell would treat as "run in the background" if the file is ever sourced. The script removes one pair of quotes. To write the lines without the URL landing in your shell history:

```bash
cd /opt/padsign
read -rs ALERT_URL                                              # paste the URL, press Enter
printf "ALERT_WEBHOOK_URL='%s'\nALERT_WEBHOOK_FORMAT=teams\n" "$ALERT_URL" >> .env; unset ALERT_URL
chmod 600 .env
./installation-scripts/monitor-status.sh --test-webhook
```

`ALERT_WEBHOOK_FORMAT=teams` can even be left out: when it is unset and the URL's host ends with `.logic.azure.com` or contains `.powerplatform.com` (the two hosts Workflows URLs use), the script uses `teams` and says so (`format teams (auto-detected: ...)`). An explicit value always wins, so a Logic App of your own that expects the `json` payload keeps getting it with `ALERT_WEBHOOK_FORMAT=json`. Setting it explicitly is still clearer for whoever reads the file next. A value other than `json` or `teams` stops the script with exit code `2` before it checks anything.

The test sends the card "PadSign monitor test from padsign.client.com - webhook works":

```text
PadSign webhook test
================================
Webhook:   https://prod-00.westeurope.logic.azure.com:443 (scheme and host only; the URL is a secret and is never printed)
Format:    teams (set by ALERT_WEBHOOK_FORMAT)
Message:   PadSign monitor test from padsign.client.com - webhook works
Result:    HTTP 202 - delivered to https://prod-00.westeurope.logic.azure.com:443.
  Teams Workflows answers 202 before its flow runs, so a 2xx does not prove the card was posted.
  If it is not in the channel within a minute, open the flow's run history (Power Automate > My flows).
```

The script counts any `2xx` as delivered, as for every receiver. For Teams that only means the workflow accepted the request, so look at the channel. If the card is missing, the flow's run history in Power Automate shows why (a wrong format is the usual one: `ALERT_WEBHOOK_FORMAT=json` against a Workflows URL).

#### Where the URL goes on an overlay-managed host

A checkout managed with `overlay.sh` ([42](42-host-reconciliation-runbook.md)) has a `.env` that `overlay.sh apply` writes from the overlay's `env` file, so a hand edit there is lost at the next apply. Use one of these:

- **The overlay's `env` file**, as a new overlay version ([42.6](42-06-living-with-an-overlay.md), *Changing a value in the overlay*). It then travels with `overlay.sh rebase` to the next release:

  ```bash
  NEW_OVERLAY=/etc/padsign/overlay/$(date +%Y%m%d)-alerting
  cp -a "$OVERLAY" "$NEW_OVERLAY"
  read -rs ALERT_URL                                              # paste the URL, press Enter
  printf "\nALERT_WEBHOOK_URL='%s'\nALERT_WEBHOOK_FORMAT=teams\n" "$ALERT_URL" >> "$NEW_OVERLAY/env"; unset ALERT_URL
  cd "$NEW"
  ./installation-scripts/overlay.sh apply  --overlay "$NEW_OVERLAY" --force
  ./installation-scripts/overlay.sh verify --overlay "$NEW_OVERLAY"
  ./installation-scripts/monitor-status.sh --test-webhook
  ```

  `OVERLAY=$NEW_OVERLAY` from here on. No container needs a restart: only this script reads these keys.

- **A root-only env file outside both**, loaded by the cron job. The environment wins over `.env`, and the file survives overlay versions and release cut-overs. For example `/etc/padsign/secrets/alert.env` (`root:root`, mode `600`, the same two lines as above, single quotes included), a symlink to the live release directory that each cut-over re-points (`/opt/padsign/current`), and a wrapper that cron runs:

  ```sh
  #!/bin/sh
  # /usr/local/sbin/padsign-monitor (root:root, mode 700)
  set -a; . /etc/padsign/secrets/alert.env; set +a
  cd /opt/padsign/current && exec ./installation-scripts/monitor-status.sh --alert --state-dir /var/lib/padsign-monitor "$@"
  ```

  ```cron
  */10 * * * * /usr/local/sbin/padsign-monitor >> /var/log/padsign-monitor.log 2>&1
  ```

  `--state-dir` outside the checkout keeps the last-run time and restart baselines across releases. Send the test through the same wrapper, so it uses the same file: `sudo /usr/local/sbin/padsign-monitor --test-webhook` (`--test-webhook` takes precedence over `--alert`).

### Exit codes

| Code | Meaning |
|---|---|
| 0 | No alerts (or report mode). `--test-webhook`: delivered (2xx) |
| 1 | Alerts fired (and were delivered, if a webhook is configured) |
| 2 | Usage error, including an `ALERT_WEBHOOK_FORMAT` other than `json`/`teams`. `--test-webhook`: `ALERT_WEBHOOK_URL` is not set |
| 3 | Alerts fired, but the webhook POST failed (non-2xx or unreachable). `--test-webhook`: not delivered |

### Payload

One `POST` with `Content-Type: application/json` per run that has alerts. With `ALERT_WEBHOOK_FORMAT=json` (the default):

```json
{
  "text": "PadSign ALERT on padsign.client.com: 1 alert(s)\n- routing_webhook_permanent_failure: webhook permanent failures: 1 since 2026-09-23T10:20:00Z\n    ps-server  | [documentRouting:webhook] PERMANENT FAILURE after retries {\"docid\":\"…\",\"url\":\"…\",\"status\":500,…}",
  "source": "padsign-monitor",
  "host": "padsign.client.com",
  "generated": "2026-09-23T10:30:00Z",
  "alerts": [
    { "key": "routing_webhook_permanent_failure", "message": "webhook permanent failures: 1 since …", "samples": ["ps-server  | [documentRouting:webhook] PERMANENT FAILURE …"] }
  ]
}
```

`text` carries everything, so a Slack incoming webhook displays it without any mapping. Microsoft Teams does not: the retired *Incoming Webhook* connector did, but a Workflows webhook fails on this payload (use `teams`, below). Other receivers can use `alerts[].key` to route. `samples` holds up to three of the matching log lines, cut at 400 bytes (a Latvian letter the cut would split is dropped, so the payload stays valid UTF-8), so a routing alert names the document that failed. `--test-webhook` sends `{"text":"PadSign monitor test from <host> - webhook works","source":"padsign-monitor","host":...,"generated":...,"test":true,"alerts":[]}`.

With `ALERT_WEBHOOK_FORMAT=teams`, the same alerts as the message the Teams Workflows template *Send webhook alerts to a channel* expects: a bold title, one text block per alert (`key: message`), its sample lines in small monospace, and a small footer with the source and time:

```json
{
  "type": "message",
  "attachments": [
    {
      "contentType": "application/vnd.microsoft.card.adaptive",
      "contentUrl": null,
      "content": {
        "$schema": "http://adaptivecards.io/schemas/adaptive-card.json",
        "type": "AdaptiveCard",
        "version": "1.4",
        "body": [
          { "type": "TextBlock", "text": "PadSign: 1 alert(s) on padsign.client.com", "wrap": true, "weight": "Bolder", "size": "Medium" },
          { "type": "TextBlock", "text": "routing_webhook_permanent_failure: webhook permanent failures: 1 since 2026-09-23T10:20:00Z", "wrap": true },
          { "type": "TextBlock", "text": "ps-server  | [documentRouting:webhook] PERMANENT FAILURE after retries {\"docid\":\"…\",…}", "wrap": true, "fontType": "Monospace", "size": "Small", "isSubtle": true, "spacing": "None" },
          { "type": "TextBlock", "text": "Source: padsign-monitor - generated 2026-09-23T10:30:00Z", "wrap": true, "size": "Small", "isSubtle": true, "separator": true }
        ]
      }
    }
  ]
}
```

The test message is a card of the same shape, titled "PadSign monitor test from <host> - webhook works". Both formats are built with the same JSON escaping, so quotes, backslashes, newlines and non-ASCII letters in log lines arrive intact.

## What fires an alert

| Key | Fires when | Threshold (env var, default) |
|---|---|---|
| `service_down` | A service active under the current compose profiles has no container, or its container is not `running` (exited, restarting, …) | - |
| `service_unhealthy` | A container's health check reports `unhealthy` ([40.1](40-01-health-checks-and-startup-order.md)) | - |
| `repeated_restarts` | A container restarted N+ times since the previous check (same container id; a recreated container starts a new count) | `ALERT_RESTART_DELTA`, 2 |
| `certificate_risk` | `nginx/certs/<host>.crt` expires within N days, or is missing/unreadable. Evaluated with `openssl x509 -checkend` | `ALERT_CERT_DAYS`, 14 |
| `archive_failure` | ps-server logged an archive upload/download failure | `ALERT_FAILURE_MIN`, 1 |
| `stamping_failure` | ps-server logged a stamping failure, including the 5xx graceful skip (`[stamp] upstream unavailable, continuing without stamp`) where the document continues **without a seal** | `ALERT_FAILURE_MIN`, 1 |
| `routing_webhook_permanent_failure` | `[documentRouting:webhook] PERMANENT FAILURE after retries` - a webhook gave up after all retries | `ALERT_FAILURE_MIN`, 1 |
| `routing_failure` | Any other routing or receive-back buffer failure (filesystem strategy error, buffer copy/sidecar failure, error webhook failure). Individual retry attempts are not counted - a later attempt may still succeed | `ALERT_FAILURE_MIN`, 1 |
| `circuit_open` | ps-server opened a dependency circuit breaker | `ALERT_FAILURE_MIN`, 1 |
| `disk_pressure` | The filesystem holding the deployment, the one holding each signed-document store (see *Disk usage* below) or, on Linux, Docker's root dir is N% full or more | `ALERT_DISK_PCT`, 85 |
| `buffer_growth` | N or more signed PDFs are waiting for Manager acknowledgement | `ALERT_BUFFER_MAX`, 100 |
| `buffer_stale` | The oldest unacknowledged signed PDF is older than N hours - a Manager desktop may be offline | `ALERT_BUFFER_MAX_AGE_HOURS`, 72 |

The buffer has no time expiry by design (a document stays until the Manager acknowledges it), so `buffer_growth` and `buffer_stale` are the only thing that notices an offline desktop or a broken Manager. Tune both to the customer's usage.

### Log window and state

The failure counts come from `docker compose logs ps-server`. In alert mode the script remembers when it last ran (`.monitor-state/state`, gitignored) and scans only logs written since then, so a failure alerts once, on the next run after it happened, and then drops out. The first run scans the last `--log-lines` (500) lines. Pass `--since 30m` (or an RFC3339 time) to override. The same state file holds per-container restart counts (for `repeated_restarts`) and the previous buffer size (printed as "Change since previous check").

Conditions that describe the current state (down, unhealthy, certificate, disk, buffer) alert on every run until fixed.

### How the failure signals are matched

Each category matches lines ps-server actually writes to its log, not the `errorCode` strings it returns in HTTP response bodies (`ARCHIVE_TIMEOUT`, `STAMP_UPSTREAM_UNAVAILABLE`, …), which never reach the log. The first version of this script grepped for those error codes, so archive failures and the stamping graceful skip always counted `0`. The patterns live at the top of the "Failure signals" section of the script.

The routing sample lines carry the docid, URL and final status only with ps-server images that include the psapp-saas#15 `logError` fix. Older images log that line as `message: '[object Object]'`; the alert still fires, it just cannot say which document failed.

### Disk usage

The report sizes the two signed-document stores, ps-server's `/signed-output` and the fallback archive's `/docs`, where the effective compose model mounts them from: `docker-compose.yml` plus `COMPOSE_FILE` (or a `docker-compose.override.yml`), read with `docker compose config`, or from the files when docker is not there (`lib/digest_gate.py mounts`, the same reader `upgrade.sh` uses). On a plain checkout that is `./signed-output` and `./docs`. On an overlay-managed checkout `compose.overlay.yml` mounts them from where the documents already are, and the line says `(signed-output, mounted from outside the checkout)`; the checkout's own `signed-output/` and `docs/` do not exist there, and the report used to print `does not exist` for both. A named volume is reported as one. When the model cannot be read (no `python3`) the checkout paths are shown, as before. The filesystem of each store that exists is checked for `disk_pressure` too, so overlay storage on its own volume is covered.

### Receive-back buffer count

The script runs a short `node` snippet inside the ps-server container (`docker compose exec`) that walks every enabled filesystem strategy's `basePath` (and `bufferPath`) and counts `<file>.meta.json` sidecars whose PDF still exists. That is the same rule `signedPdfBuffer.rebuildFromDisk()` uses, so the count equals the pending index size, and it works with any ps-server image; no endpoint or image change is needed. It also reports the age of the oldest entry.

## Verified

- psapp-saas's integration suite (`server/test/integration/`, scenario 7) runs `monitor-status.sh --alert` against a live stack after forcing a webhook permanent failure, with `ALERT_WEBHOOK_URL` pointed at a local receiver. It asserts the receiver gets exactly one JSON POST containing a `routing_webhook_permanent_failure` alert whose samples and `text` name the failed docid, and that a webhook which fails twice and then recovers raises no such alert.
- `installation-scripts/tests/test-alert-webhook.sh` (hermetic: stub `docker`, a local receiver on `127.0.0.1`) checks both formats against the requests the receiver records: the `json` payload byte for byte, the `teams` card's structure, auto-detection by host, escaping of quotes, backslashes, newlines and Latvian letters, `--test-webhook`, that no URL path, query or auth header is ever printed or on `curl`'s command line, and the *Disk usage* stores on a plain and an overlay-managed checkout. It cannot post to a real Teams channel, so after setting up Teams run `--test-webhook` and look at the channel.
- A standalone `--alert` run against the same stack fired `routing_webhook_permanent_failure`, `routing_failure` and `disk_pressure` (the dev machine's disk really was 96% full) in about 16 seconds.

## What this does not do

- It is not a metrics store or a paging system. It posts to one webhook; escalation, on-call routing and de-duplication across hosts belong to whatever receives it.
- It watches one host. Several deployments each need their own cron entry.
- `dmss-digital-stamping-service` exposes `/actuator/prometheus`, and the other DMSS services could with a one-line `management.endpoints.web.exposure.include` change, if the organisation later adopts Prometheus. Nothing here depends on that.
