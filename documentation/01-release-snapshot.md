# 1. Release Snapshot

> This file describes what each released tag *contains*. The minimum tag a given
> capability *requires* lives in `release/capabilities.json`, which `upgrade.sh`
> and `toggle-features.sh` read at run time - cite that file rather than copying
> a number out of it. The exact `sha256` digest approved for each tag below lives
> in `release/approved-digests.json` - cite that file rather than copying a
> digest out of it. See [39. Release Procedure](39-release-procedure.md).

Every image `docker-compose.yml` references is pinned `tag@sha256:digest`, not
by tag alone; `installation-scripts/validate-config.sh` fails a deployment
whose pin doesn't match `release/approved-digests.json`.

- `ps-server`: `mihailsgordijenko/ps-server:3.30` (first `ps-server` release built by CI (`psapp/.github/workflows/build-and-push.yml`) from the `ps-server/3.30` tag push, so it carries an SPDX SBOM and a `mode=max` SLSA provenance attestation whose builder is the GitHub Actions run, on top of the OCI labels `:3.28` had; not cosign-signed yet. `3.29` was a CI-verification tag and was never released. **Runtime moves from `node:18-alpine` (EOL) to `node:24-alpine` and the container now runs as the non-root `node` user (uid 1000), not root** (psapp-saas#14). Existing `signed-output/` trees written by a root image are not writable by it; `upgrade.sh` re-owns the tree to the image's uid before recreating the container and stops if it can't (see `installation-scripts/lib/dir-permissions.sh` and step 5 of [5.1](05-01-what-upgrade-does-step-by-step.md)). Rolling back to `:3.28` needs nothing, root writes into a uid-1000 tree fine. Production dependency tree remediated from 29 vulnerabilities (13 high, 4 critical) to 3 low: the unused `request` package is removed and `pdfjs-dist` moves to 4.x. Behaviour changes a deployment should know about: filesystem routing is now a **durable archive** by default, so acking a Manager pickup no longer deletes the archived file under `signed-output/{company}/{email}/...`; the receive-back buffer gets its own hard-linked copy under `<basePath>/.padsign-buffer/` instead, and `signed-output/` now grows until you prune it. Set a strategy's `bufferOnly: true` to keep the old delete-on-ack behaviour (psapp-saas#17). The receive-back endpoints now check ownership (psapp-saas#18): `GET /api/signedPdf?docid=` and `POST /api/signedPdf/ack` only act on a document the caller can prove it owns, either through a new optional per-company key in `REGISTER_PDF_API_KEYS` (capability `per-company-api-keys`) or, under the legacy shared `REGISTER_PDF_API_KEY`, by sending the matching `email` + `company`. **The current Padsign Manager (v1.2.0) sends only `docid` on those two calls, so on a deployment that uses receive-back with the legacy key, Manager delivery stops after upgrading (both calls return `404`, documents stay pending on the server and nothing is lost).** Before upgrading such a deployment, move each receive-back company to a `REGISTER_PDF_API_KEYS` entry (config only, no Manager change; recipe in psapp's `docs/document-routing-spec.md`, *Migrating to per-company keys*), or ship a Manager build that sends `email` + `company`. Deployments without receive-back are unaffected. Fixes: `POST /api/signedPdf/ack` returns `500` and keeps the entry pending when the buffered files can't be deleted, instead of `200 {removed:true}` followed by a second delivery after restart; `/api/stamp` retries now resend the full multipart body, so one upstream 5xx no longer turns into two 30 s timeouts, a 504 and a tripped circuit breaker; and the webhook `PERMANENT FAILURE` log line now carries the docid, URL and status on one line, which is what `monitor-status.sh --alert` keys on. Retains everything from `:3.28`: the receive-back buffer + endpoints from `:3.27` (only returning documents when `DOCUMENT_ROUTING.enabled` + the `filesystem` strategy are enabled), the `:3.28` receive-back fixes (#16, #19, #21, #22), and the `STAMP_MODE` local e-sealing dispatch from `:3.26`. See `documentation/35-receive-back-deployment-runbook.md`.)

Not cosign-signed yet. No application change: the SPA source is the same as `:8.39` (the only `client/` changes since are test suites and a test-only dev dependency), the image is just rebuilt on the same `nginx:1.27-alpine` line. Retains everything from `:8.39`: the Keycloak-Bearer-token archive-PDF download from `:8.38`, so `GET /archive/api/document/{docid}/download` can be closed behind authentication at nginx (see `documentation/22-security-and-route-protection.md`; capability `closable-download-route`, `release/capabilities.json`), and the automatic dark-mode support from `:8.37`.)
